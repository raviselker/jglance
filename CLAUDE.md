# Claude guidance for `jglance`

A jamovi module that renders an interactive **Data Overview** analysis: scannable variable list with sparklines, auto-detected data-quality notes, and per-variable detail panels. R6 analysis on the back, Vue 3 + Vite SVG-and-HTML UI on the front, glued together by jamovi's `Html` results element loading a UMD bundle.

Both you and any future contributor should read this before touching the code — it captures conventions and the gotchas that bit me while building this thing.

## Dev cycle

**Iterating on the UI** (fast — no R or jamovi needed):
```bash
cd client
npm install   # first time only
npm run dev   # serves index.html with fixture data
```
The harness mounts the Vue app against a fixture sized like jamovi's narrow column. Edit `src/` and Vite hot-reloads.

**Installing into jamovi** (full integration):
```bash
./scripts/build-and-install.sh
```
Builds the client bundle to `inst/`, then runs `jmvtools::install()` which compiles the YAMLs, regenerates `R/overview.h.R`, and installs the module into your local jamovi library. **Restart jamovi** (fully — not just the analysis) after install to pick up UI changes.

**Regenerating the demo dataset**:
```bash
Rscript scripts/generate-demo-data.R
```
Needs `jmvReadWrite` installed if you want the `.omv` (descriptions + measure types preserved). The CSV is always written.

## The R ↔ JS bridge (technique copied from `jamovi/besoplots@laiton`)

1. R6 analysis class returns an `Html` results item.
2. In `.init`, attach a UMD script: `dashboard <- self$results$x; dashboard$scripts <- c('jglance.umd.js')`.
3. In `.run`, compute data → `jsonlite::toJSON(...)` → `setContent()` with a `<div id="elemXXX">` placeholder + an inline `<script>` that polls for the global `Jglance` namespace, then calls `Jglance.createOverview("#elemXXX", data)`.
4. Vue mounts inside the placeholder.

The bundle exposes `window.Jglance = { createOverview, PlotStateStore }`. State persists across jamovi re-renders via `sessionStorage` keyed by `jglanceState` (or a per-instance namespace).

## Conventions

### CSS scoping
All design tokens are defined under `.jglance` (in `tokens.css`). The root element of every analysis renders with `class="jglance jglance--<analysisName>"`. **If you forget `class="jglance"`, every `var(--...)` falls back to invalid → silently broken layout** (the most common cause of "why is the sparkline solid black?").

### Variable type taxonomy
Driven by the union in `common.ts`:
- `continuous` — numeric, gets histogram + 6-stat grid + quartile ticks
- `nominal` / `ordinal` — gets level bars; level order is the factor's defined order (`levels(v)`), **not count order** (critical for ordinal)
- `id` — gets a sample-grid + count, no distribution chart

### Naming
- File slugs: `kebab-case.vue`, snake_case for R
- Component classes: BEM-ish (`.row__name`, `.list__item.is-expanded`)
- TypeScript interfaces: `I` prefix, e.g. `IVariableSummary`

## Gotchas (each cost me time)

### 1. `compilerMode: aggressive` in `.u.yaml` overwrites the file on every install
The compiler regenerates the UI from the option list every time, silently wiping manual edits like `permitted: id` on the supplier. **Use `compilerMode: tame` once the UI is hand-customized.**

### 2. `permitted` lives in two places
- In `.a.yaml` on the option (server-side check — rejects on submit)
- In `.u.yaml` on the `VariableSupplier` AND `VariablesListBox` (client-side filter — controls what's draggable / what gets grayed out)

To accept ID-type columns, both layers need `permitted: [numeric, factor, id]`. Without the supplier-level one, ID columns appear grayed out. Source of truth: `jmv/jamovi/descriptives.u.yaml`.

### 3. `jsonlite::toJSON(auto_unbox = TRUE)` unboxes single-element vectors
For a constant-value variable, `histogram$counts` is length 1, so `[80]` serializes as `80`. JS then trips on `.length`/`Math.max(...n)` and renders nothing. **Wrap arrays-that-might-be-length-1 with `I()`**:
```r
histogram = list(edges = I(h$breaks), counts = I(as.integer(h$counts)))
```

### 4. `null` in a named list serializes to `{}`, not `null`
Same `toJSON` call: `description = NULL` becomes `"description": {}` (empty object, truthy in JS). Fix: pass `null = "null"` to `toJSON`. We do this for both R6 classes.

### 5. R6 nested assignment surprise
```r
self$results$item$scripts <- c('foo.js')   # ERROR: unused argument <environment>
```
R's `x$a$b <- v` syntax tries to write `tmp$b <- v` then assign `tmp` back to `x$a`. The write-back invokes the active binding as a *setter*, which fails for read-only bindings. **Use a local variable**:
```r
item <- self$results$item
item$scripts <- c('foo.js')
```

### 6. jamovi column attribute names
At analysis time, jamovi's engine attaches `jmv-id` (boolean) and `jmv-desc` (string) to columns. `jmvReadWrite` uses a different set of attributes when round-tripping `.omv` files (`description`, `measureType`, etc.). The detection in `overview.b.R` checks both `jmv-id` and `jmv-measure-type` as fallback.

### 7. Factor level order matters
`sort(table(x), decreasing = TRUE)` reorders by count — destroys ordinal meaning. **Always iterate `levels(v)` in definition order** when emitting level lists. Compute "dominant" on the JS side by scanning the array.

### 8. `category: plots` vs `analyses`
Set in `.a.yaml`. Plot modules appear in the Plots tab; everything else in Analyses. This module is `category: analyses`.

### 9. jamovi has no dark mode (yet)
Don't use `@media (prefers-color-scheme: dark)` for jamovi-facing CSS — the user's OS preference shouldn't theme an embedded analysis. Use explicit `[data-theme='dark']` selectors only (useful for the dev harness).

### 10. CSS-variable scoping for embedded analyses
The dev harness mounts at a fixed width (~560px) to mimic jamovi's narrow results column. jamovi imposes its own width limit on `Html` results that **cannot be overridden from inside** (we tried `min-width: 720px` etc. — silently clamped). Design for ~500px wide.

## Validation gates

Before considering a change shippable, run:

```bash
cd client && npm run build    # vue-tsc + vite build (both strict)
```

If touching R: do a full `./scripts/build-and-install.sh` and verify in jamovi at least once. The JS bundle build doesn't catch R-side issues.

## When to extend

The module currently has one analysis (`overview`). To add another:
1. New `jamovi/<name>.{a,r,u}.yaml`
2. New `R/<name>.b.R` (use a local-variable assign for `$scripts`, see gotcha #5)
3. Optionally new client-side composer + widgets under `client/src/`
4. Export a new factory from `main.ts` (e.g., `createX`) and attach to `window.Jglance`
## Committing

- **Small logical commits** — break changes into small, focused commits with a single purpose.
- **Commit title** — a single sentence in imperative mood, max 50 characters, no trailing dot, no type prefixes (e.g. no "feat:", "fix:").
- **Optional description** — only to clarify functional choices (the "what" and "why"). Do not explain the "how" or anything already evident from the diff. Max line length 72 characters.
- **No AI mentions** — never mention AI assistants or tools in commit messages.
- **Propose first** — always propose a draft commit message for the user to approve before committing.
